# Задача 8. Экспорт базы знаний ЭС в Mermaid

## Постановка

Сейчас база знаний экспертной системы хранится в БД `EsDb` (MSSQL) в реляционных таблицах.

База знаний может быть представлена в виде графа: нода первого вопроса, от неё связи с
нодами-вариантами ответов, дальше следующие вопросы и так далее до вывода цели консультации.
Последовательность вопросов определяется механизмом логического вывода; алгоритм — в
`EsConsultationServices`, класс `ConsultationEngine`.

Цель — вектор, то есть набор свойств, поэтому листья графа — это собственно эти свойства.
Пример графа в формате yEd — в файле `Дополнительные файлы/Схема БЗ.graphml`
(вверху все возможные свойства, ниже сам граф). Сейчас это дерево, но так может быть не всегда.

Нужно:

1. Добавить в `EsServices` функцию преобразования (экспорта) базы знаний в формат Mermaid.
2. В `EsUi` добавить пункт меню «Экспорт» для вызова этой функции.
3. Экспортировать только ЭС «Фильмы»: остальные записи в базе — архивные версии этой ЭС,
   нужна только последняя.
4. Консультации не экспортировать: нужны именно правила, чтобы можно было понять,
   как работает механизм логического вывода.
5. Файл по умолчанию называется `expert-system-[yyyy-MM-dd].mmd`.

## Что выяснено при исследовании

- В локальной `EsDb` три ЭС: `Фильмы` (Id 18, активная, `TargetId = 211`) и две архивные
  `Фильмы_auto_*` без цели. Активную версию можно надёжно найти по точному имени `Фильмы`
  (архивные содержат суффикс `_auto_`). Если точных совпадений несколько — берётся запись
  с наибольшим `Id`.
- В ЭС «Фильмы» 20 переменных, 27 правил. Все условия правил — запрашиваемые переменные
  (`VariableType.Queriable`), вывод — `Совет = <GUID>` (`VariableType.Detective`).
  Промежуточных выводимых фактов сейчас нет, но экспорт должен поддерживать и общий случай:
  результат одного правила может быть условием другого.
- Значения домена `#Советы` — GUID советов из `FilmsDb`; человекочитаемое описание совета
  уже строится `FilmDb.IAdviceRepository.GetDescriptionsAsync` и представляет собой вектор
  свойств, например: `Волшебный (100); Детский (100)`.
- `EsServices.ExpertSystemService.GetAsync` уже собирает `ExpertSystemVM` с этими описаниями,
  поэтому экспорт не требует доступа к консультациям и движку.
- Порядок правил (`Rule.Order`) важен: движок перебирает правила цели по возрастанию `Order`
  и срабатывает первое, у которого все условия истинны.

## Выбранное решение

### Формат Mermaid — цепочки «вопрос → ответ → … → лист»

Один файл `*.mmd` с диаграммой `flowchart TD`. Узлов правил нет: правило выражается
цепочкой вопросов и ответов, а его номер и имя пишутся на финальной стрелке к листу.

Пример одной цепочки:

```text
[С кем смотреть?] -> (С семьей) -> [Какой состав?] -> (Есть дети до 10 лет) -> <[Совет: Волшебный (100); Детский (100)]>
```

Правила построения:

- вопрос — прямоугольный узел с текстом вопроса (`Variable.Question`, иначе имя переменной);
- вариант ответа — овальный узел со значением домена;
- лист — шестиугольник с подписью `«Совет = <вектор свойств>»`;
- условия правила в его порядке (`Rule.Order`, затем `Condition.Order`) образуют цепочку:
  вопрос → ответ → следующий вопрос → ответ → … → лист;
- ответы, общие для нескольких правил с одинаковым префиксом, переиспользуются:
  граф строится как дерево/бор (trie) по последовательностям условий. Одинаковый вопрос
  в разных ветках — это разные узлы (как в `Схема БЗ.graphml`);
- под каждым узлом вопроса показываются все варианты ответа из домена, даже если из
  конкретного ответа не выведено ни одного совета (тупиковая ветка);
- на стрелке от последнего ответа к листу — подпись `«{Order + 1}. {Name}»`;
  так видны имя и порядок правила;
- пустой ответ на вопрос или отсутствие подходящего правила даёт тупиковую ветку
  без листа;
- если результат правила используется как условие другого правила, узел-факт остаётся
  шестиугольником и связывает цепочки между собой;
- листья дедуплицируются по паре «переменная + значение»: одинаковый вывод разных
  правил даёт один лист с несколькими входящими стрелками;
- в шапке файла — комментарии Mermaid (`%%`) с именем и Id ЭС, датой экспорта, целью,
  легендой форм узлов, пояснением про порядок условий в цепочке и про то, что правила
  проверяются по порядку и срабатывает первое подходящее;
- типы узлов различаются `classDef` (вопрос, ответ, свойство, некорректное правило).

### Слой EsServices

Новые файлы в `EsServices/Services/Export/`:

1. `ExpertSystemMermaidExporter` — чистый форматтер `ExpertSystemVM -> string`.
   Не зависит от БД и UI; удобен для тестов.
2. `IExpertSystemExportService` и `ExpertSystemExportService`:
   - находит ЭС с точным именем `Фильмы` (при нескольких — максимальный `Id`);
   - загружает её через существующий `IExpertSystemService.GetAsync`;
   - вызывает форматтер;
   - возвращает результат: Id и имя ЭС, содержимое файла и имя по умолчанию
     `expert-system-{yyyy-MM-dd}.mmd` (локальная дата);
   - если ЭС не найдена — понятное `KeyNotFoundException`.

Регистрация сервисов — в `EsUi/Program.cs`.

### Слой EsUi

- В `Shared/NavMenu.razor` — пункт меню «Экспорт» (иконка скачивания), маршрут `/export`.
- Новая страница `Pages/ExpertSystemExport.razor`:
  - при открытии формирует экспорт и показывает имя файла, счётчики и предпросмотр текста;
  - кнопка «Скачать» сохраняет файл с именем по умолчанию;
  - ошибки (нет ЭС, проблема с БД) показываются в `alert`, есть возможность повторить;
- скачивание — через JS-interop и `DotNetStreamReference` (стандартный механизм Blazor Server
  для файлов), JS-функция добавляется в `wwwroot/js/`.
- Экспорт формируется только по кнопке/открытию страницы, никаких фоновых заданий и
  изменений в БД нет.

### Тесты

В `EsServices.Tests`:

- форматтер: цепочка вопрос → ответ → следующий вопрос → … → лист; несколько условий
  одного правила дают цепочку; общий префикс правил переиспользуется; одинаковый вопрос
  в разных ветках даёт разные узлы; одинаковый результат двух правил даёт один лист;
  экранирование кавычек и переводов строк; правило без вывода не ломает экспорт;
- сервис экспорта: выбирается именно `Фильмы`, архивные версии игнорируются;
  имя файла соответствует `expert-system-yyyy-MM-dd.mmd`.

### Документация

- README: в разделе `EsServices` — экспорт БЗ, в разделе `EsUi` — пункт «Экспорт».

## Что входит в задачу

1. Форматтер БЗ в Mermaid в `EsServices`.
2. Сервис поиска ЭС «Фильмы» и получения готового экспорта.
3. Регистрация сервисов в `EsUi`.
4. Пункт меню «Экспорт» и страница с предпросмотром и скачиванием файла.
5. Тесты форматтера и выбора ЭС/имени файла.
6. Обновление README.

## Что не входит в задачу

- Экспорт консультаций, сессий, ответов и показанных фильмов.
- Экспорт архивных версий ЭС и выбор произвольной ЭС в UI.
- Изменение движка вывода и модели БД, миграции.
- Рендеринг Mermaid внутри `EsUi` (только формирование и скачивание `.mmd`).
- Экспорт в другие форматы (yEd/GraphML, Draw.io, PlantUML).

## Критерии готовности

- `EsServices` и `EsUi` собираются.
- Экспорт содержит только активную ЭС «Фильмы», без архивных версий и консультаций.
- В графе есть все 27 правил: цепочки вопросов/ответов и листья-советы; на финальной
  стрелке каждой цепочки — номер и имя правила.
- Листья подписаны вектором свойств совета (из `FilmsDb`); при отсутствии описания
  используется GUID.
- Общий префикс правил переиспользуется, а одинаковый вопрос в разных ветках показан
  отдельными узлами (как в `Схема БЗ.graphml`).
- Порядок правил отражён в подписи финальной стрелки и в легенде.
- Файл по умолчанию называется `expert-system-{yyyy-MM-dd}.mmd` и скачивается из UI.
- Новые тесты проходят; существующие тесты `EsServices.Tests` не регрессируют.

## Проверка

- `dotnet build EsServices/EsServices.csproj`
- `dotnet build EsUi/EsUi.csproj`
- `dotnet test EsServices.Tests/EsServices.Tests.csproj`
- Ручной сценарий: открыть `EsUi` → «Экспорт» → проверить предпросмотр → скачать файл →
  вставить содержимое в Mermaid Live Editor и убедиться, что диаграмма строится.
- Проверить, что в файле нет архивных `Фильмы_auto_*` и нет данных консультаций.
